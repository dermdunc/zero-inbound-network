# Decisions: Zero-Inbound Network

## ADR Log

| Date | Decision | Rationale |
|---|---|---|
| 2026-08-28 | Initial scaffold as factory-output | A public, sanitized reference implementation of a zero-inbound AWS network fronted by Cloudflare Access, with GitHub+Google SSO and per-app Terraform module reuse |
| 2026-08-28 | Zero-inbound security group (no ingress rules at all) instead of a NAT gateway + private subnet + bastion/allowlist design | The workload is a small number of apps for a small, named set of people. A NAT gateway alone costs more per month than the entire rest of this stack combined, and defending an inbound path that doesn't need to exist is strictly more attack surface than removing it. Documented as a deliberate single-control tradeoff in `docs/well-architected.md`, with the dual-control alternative named for when it's the wrong call (a compliance regime requiring defense-in-depth). |
| 2026-08-28 | Cloudflare Access with two parallel identity providers (GitHub OAuth, Google OAuth) rather than one | A single-IdP design is simpler but assumes everyone who needs access already has that one account type. Registering both as account-wide `cloudflare_zero_trust_access_identity_provider` resources and referencing both from every app's policy costs one extra Terraform resource and OAuth app registration, and removes that assumption. Each app's policy still requires an exact email (or optional Workspace-domain) match on top of the IdP — the IdP choice grants authentication, not authorization. |
| 2026-08-28 | GitHub Actions OIDC -> short-lived STS role per app, no long-lived AWS access keys anywhere | A leaked long-lived key is a standing liability with no expiry; a leaked repo secret under OIDC can only assume a role scoped to that one repo, for as long as the token is valid. The OIDC provider itself is registered once per AWS account (`create_github_oidc_provider` variable exists specifically because AWS rejects a second provider for the same issuer URL in one account) — most adopters of this pattern will already have one from another stack and should set it to `false`. |
| 2026-08-28 | One reusable Terraform module (`modules/hosted-app/`) per app, called from root `main.tf`, instead of one flat set of resources per app copy-pasted | The point of the pattern is that adding a second hosted app is a `module` block, not a second set of hand-maintained resources that drift from each other over time. Everything app-specific (SG, IAM roles, ECR repo, tunnel, Access application/policy, ECS service/task-def) lives in the module; only the two account-wide Cloudflare identity providers and the shared VPC/ECS cluster live in root. |
| 2026-08-28 | `terraform validate` run and fixed to green; no `terraform apply` run, no backend configured | This repo is a reference implementation, not a deployed instance — see `infra/terraform/versions.tf`'s comment. Two real schema errors were caught by `validate` and fixed: an AWS security-group rule description containing an em dash, which AWS's description-field regex rejects; and a Cloudflare Access policy's Google-Workspace-domain match, which needed the plain `email_domain` list attribute on `include`, not the `gsuite` nested block (which matches specific Workspace Groups and requires its own `identity_provider_id`, not a bare domain). |
