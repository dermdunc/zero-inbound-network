# Decisions: Zero-Inbound Network

## ADR Log

| Date | Decision | Rationale |
|---|---|---|
| 2026-08-28 | Initial scaffold as factory-output | A public, sanitized reference implementation of a zero-inbound AWS network fronted by Cloudflare Access, with GitHub+Google SSO and per-app Terraform module reuse |
| 2026-08-28 | Zero-inbound security group (no ingress rules at all) instead of a NAT gateway + private subnet + bastion/allowlist design | The workload is a small number of apps for a small, named set of people. A NAT gateway alone costs more per month than the entire rest of this stack combined, and defending an inbound path that doesn't need to exist is strictly more attack surface than removing it. Documented as a deliberate single-control tradeoff in `docs/well-architected.md`, with the dual-control alternative named for when it's the wrong call (a compliance regime requiring defense-in-depth). |
| 2026-08-28 | Cloudflare Access with two parallel identity providers (GitHub OAuth, Google OAuth) rather than one | A single-IdP design is simpler but assumes everyone who needs access already has that one account type. Registering both as account-wide `cloudflare_zero_trust_access_identity_provider` resources and referencing both from every app's policy costs one extra Terraform resource and OAuth app registration, and removes that assumption. Each app's policy still requires an exact email (or optional Workspace-domain) match on top of the IdP — the IdP choice grants authentication, not authorization. |
| 2026-08-28 | GitHub Actions OIDC -> short-lived STS role per app, no long-lived AWS access keys anywhere | A leaked long-lived key is a standing liability with no expiry; a leaked repo secret under OIDC can only assume a role scoped to that one repo, for as long as the token is valid. The OIDC provider itself is registered once per AWS account (`create_github_oidc_provider` variable exists specifically because AWS rejects a second provider for the same issuer URL in one account) — most adopters of this pattern will already have one from another stack and should set it to `false`. |
| 2026-08-28 | One reusable Terraform module (`modules/hosted-app/`) per app, called from root `main.tf`, instead of one flat set of resources per app copy-pasted | The point of the pattern is that adding a second hosted app is a `module` block, not a second set of hand-maintained resources that drift from each other over time. Everything app-specific (SG, IAM roles, ECR repo, tunnel, Access application/policy, ECS service/task-def) lives in the module; only the two account-wide Cloudflare identity providers and the shared VPC/ECS cluster live in root. |
| 2026-08-28 | `terraform validate` run and fixed to green; no `terraform apply` run, no backend configured | This repo is a reference implementation, not a deployed instance — see `infra/terraform/versions.tf`'s comment. Two real schema errors were caught by `validate` and fixed: an AWS security-group rule description containing an em dash, which AWS's description-field regex rejects; and a Cloudflare Access policy's Google-Workspace-domain match, which needed the plain `email_domain` list attribute on `include`, not the `gsuite` nested block (which matches specific Workspace Groups and requires its own `identity_provider_id`, not a bare domain). |
| 2026-08-28 | Doubt-driven-developed the Terraform and docs (a single-model adversarial review, then an independent Codex cross-model review), and fixed every valid-actionable finding from both, at direct user request | Two genuinely severe findings, both real security defects: (1) the Access application never set `allowed_idps`, so Cloudflare defaulted it to every IdP on the account rather than just the two this module creates - the "two parallel IdPs" contract was not actually enforced by any resource. Fixed by passing `allowed_idps` explicitly. (2) The Google-Workspace-domain allow-list (`email_domain`) is IdP-agnostic in Cloudflare's own model - a matching email domain authenticated through any IdP, not just Google, would have satisfied it. Fixed by splitting into two policies and adding a `require { login_method = [google_idp_id] }` block to the domain-match policy specifically. Also fixed: the GitHub OIDC deploy-role trust used `StringLike` with no `github_repo` format validation, making a wildcard trust constructible; switched to `StringEquals` with strict `owner/repo` validation and no default. The trust's second alternative pattern (`environment:production`) was removed - it does not actually restrict which branch can assume the role unless a GitHub Environment deployment-branch policy is separately configured, which nothing here creates; the comment claiming an "ID-augmented sub-claim form" was handled was false and removed rather than implemented on an unverified assumption. Also fixed: an explicit `thumbprint_list = []` (should be omitted per the AWS provider's optional+computed schema, an apply-time failure risk as written); `name_prefix` documented as applying to every resource but not actually threaded into the module (now is, everywhere); no validation that the SSM parameter path starts with `/`; the ECS execution role's ECR permissions scoped to `Resource = "*"` where scoping was possible; `iam:PassRole` with no `iam:PassedToService` condition; both `cloudflared:latest` and the example `nginx:latest` unpinned; the Access allow-list variables allowing a constructible fail-open (`allowed_emails = []` and `allowed_google_domain = null` together); a comment referencing `app.tf.example` as an existing file that was never created (now created). Two findings disclosed in docs rather than code-fixed: unrestricted egress (a residual exfiltration/C2 risk the "zero inbound" framing never mentioned) and plaintext secrets in Terraform state (ships with no backend by design; whichever gets configured before a real apply must be chosen for encryption, not just locking). `terraform validate` re-run clean after all fixes. |
| 2026-08-29 | Added an explicit "standalone example, no ties to any shared Terraform library" disclosure to README.md and docs/well-architected.md; ran the newly-named FOSS Publication Workflow's 6 gates | User asked directly whether this repo should be a pure example with no connection to any private/shared Terraform machinery - verified true (grepped the whole infra/terraform/ tree for backend/remote-state/shared-module references, zero matches beyond the comment explaining why) and made the guarantee explicit in the docs rather than leaving a reader to verify it themselves. Gate 3: LICENSE already present (MIT). Gate 4 (new - community-health baseline): added CONTRIBUTING.md (with a solo-maintainer honesty section), CODE_OF_CONDUCT.md (condensed Contributor Covenant 3.0), and .github/ISSUE_TEMPLATE + PULL_REQUEST_TEMPLATE.md, all repo-specific rather than generic boilerplate. |
| 2026-08-29 | Doubt-driven-developed this same pass (a fresh adversarial review), found and fixed real defects rather than a clean pass | Most severe: the entry directly above originally claimed "Gate 1: clean, 0 HOLD/PATH" while itself containing a literal machine path in its own text (this row's own citation of the workflow doc's location) - the ledger entry recording the gate pass was the thing that broke the gate. Removed the literal path from this file; re-ran the real script after the fix: `secret-sauce-audit.sh` now genuinely exits 0 (0 HOLD, 0 PATH, 3 IDENTITY hits, all confirmed as the intended dermdunc public identity - .hekton/project.yaml, docs/next-actions.md, LICENSE). Also found and fixed: the prior entry claimed "full 6 gates" run but only reported evidence for 3 of them - Gates 2, 5, 6 are recorded honestly now, not asserted; AGENTS.md documented a verification command (`scripts/verify-project.sh`) that is gitignored and fails on a real clone, same bug already fixed in docs/setup.md but missed here - fixed; CONTRIBUTING.md and the PR template referenced `modules/hosted-app/` when the real path is `infra/terraform/modules/hosted-app/`, and called `app.tf.example` an "existing caller" when it's a template Terraform never loads - both fixed; CODE_OF_CONDUCT.md was structured like Contributor Covenant 2.1 while the workflow doc cited it as condensed from 3.0 - rewritten to actually follow 3.0's section structure; the workflow doc's own citation of Agentic Tekton's `proof-doctrine.md` as authority for this repo's disclosure requirement overstated that doc's scope (it governs Keystone Gremlin's blog-content review specifically, not a factory-wide policy) - reworded as a borrowed instinct, not a shared authority; a leftover "Gate 4's job, not Gate 1's" cross-reference in the workflow doc, from before the community-health gate was inserted as the new Gate 4, should have read "Gate 5's job" - fixed; agents/index.md's one-line Gremlin description was stale, missing Gate 2 and the new Gate 4 - fixed.
