# Open Source Council Review — 2026-08-29

First real run of the Open Source Council (`~/hekton/gremlins/oss-council/open-source-council.md`), Gate 7 of the FOSS Publication Workflow. Run against this repo after Gates 1-6 were confirmed clean. Five personas reviewed independently and in parallel, no persona saw another's critique before writing its own.

## Synthesis

**Convergence, not disagreement.** Four of five personas (New Contributor, Security-Conscious Reviewer, License & Provenance Reviewer, Brand & Positioning Reviewer) came back clean or strongly positive, with only minor, non-blocking observations. This is reported honestly as genuine convergence, not smoothed-over disagreement — there was no real split between personas to paper over.

**One real, substantive finding**, from the Skeptical Outsider: the README's and architecture doc's "reuse story made literal" framing overstates what's actually been demonstrated. The repo has exactly one real module instantiation (`main.tf`'s `example_app`, an nginx demo with `desired_count = 0`); `app.tf.example` is a template Terraform never loads, never filled in, never validated as a second real call site. `terraform validate` therefore only ever type-checks the module against one caller. The claim of proven reuse rests on an untested template, not a second demonstrated instance.

**Two optional, non-blocking observations**, one each from Security-Conscious Reviewer and Brand & Positioning Reviewer — neither rises to a required fix.

## Prioritized Action List

1. **(Medium — the one real finding)** Either soften the "reuse story made literal" language in `README.md` and `docs/architecture.md` to acknowledge the second-app path is a template, not yet exercised — or close the gap for real: fill in `app.tf.example` as an actual second `module` block (even a trivial demo app) and confirm `terraform validate` passes with two real call sites, not one. The second option is the stronger fix and directly demonstrates the thesis rather than just claiming it.
2. **(Low, optional)** Add a minimal example GitHub Actions workflow (`.github/workflows/deploy.yml.example` or similar) demonstrating the `permissions: id-token: write` block and the OIDC-based deploy flow the Terraform is built for — closes the implicit-assumption gap the Security-Conscious Reviewer noted. Not unsafe as-is, just an unstated assumption a copier has to supply themselves.
3. **(Low, optional, stylistic)** Trim "the dark switch" branding phrase and/or the "the absence is the control" framing, which repeats near-verbatim across README.md, `docs/architecture.md`, and `docs/well-architected.md` — noticeable to a reader working through all three in sequence, as the README's own "Key Docs" list invites. Purely a tightening pass, not a correctness issue.

## Per-Persona Critiques

### New Contributor

Nothing wrong found. Read README.md, CONTRIBUTING.md, CODE_OF_CONDUCT.md, both issue templates, and PULL_REQUEST_TEMPLATE.md, and actually executed every verification command they quote.

Verified findings:

- README.md clearly states what the repo is in the first two lines, explains the pattern in five numbered steps before any code, with no assumed context. "Implementation Status" is upfront that nothing is deployed. Quick Start commands work as documented.
- CONTRIBUTING.md's commands are real and accurate — ran `terraform init -backend=false && terraform validate` from scratch (deleted `.terraform/` and lock file first), succeeds cleanly, no credentials needed, matching the doc's claim exactly. `terraform fmt -recursive -check` also exits 0.
- PR template checklist references real, existing paths: `infra/terraform/main.tf`'s `example_app` module block, and `infra/terraform/app.tf.example` (correctly described as never loaded by Terraform).
- Solo-maintainer section reads as calibrated honesty, not overpromising — no SLA claims, no false response-time guarantees.
- Issue templates point to real files (well-architected.md's tradeoffs section exists and covers what's claimed).
- CODE_OF_CONDUCT.md is at repo root, linked from both README.md and CONTRIBUTING.md — a new contributor hits it either way, and GitHub also surfaces root-level CODE_OF_CONDUCT.md automatically.

Neutral note, not a defect: AGENTS.md's instruction not to reference the broken `verify-project.sh` in reader-facing docs is being followed correctly — it isn't referenced anywhere a human contributor would see.

### Security-Conscious Reviewer

No new findings after thorough cross-referencing of README/architecture/well-architected claims against `modules/hosted-app/main.tf`. Every claim checked is either accurate or explicitly hedged:

- "Zero ingress" is real (no `ingress` block in the SG) — unrestricted egress is already disclosed as residual risk in both the SG's inline comment and well-architected.md.
- `allowed_idps` restriction, the two-policy IdP-scoped Access design, and exact-match (`StringEquals`) OIDC trust all match what the code does — these are the exact defects the prior DDD pass fixed, and the fixes are present and correctly implemented, not just claimed.
- `variables.tf` enforces "at least one of `allowed_emails`/`allowed_google_domain` must be set" as a hard `validation` block, not just a doc note — a copier cannot `terraform apply` with a fail-open Access policy by accident.
- `terraform.tfvars.example` uses placeholder values only; no real account IDs, emails, or credentials found anywhere in tracked files.
- State-file plaintext-secrets risk is explicitly disclosed in well-architected.md's "State" section, including that `sensitive = true` doesn't protect the state file itself.
- `cloudflared_image` has no default and the variable description explicitly warns against pinning `:latest`.

One minor observation, not a defect: no actual `.github/workflows/*.yml` exists demonstrating the `permissions: id-token: write` block a copier would need for the documented OIDC deploy flow. Not unsafe — just an implicit assumption a copier has to supply themselves.

### Brand & Positioning Reviewer

**Verdict: genuinely strong, distinctive work — not filler.** Does not read like a generic Terraform showcase repo.

What makes it distinctive:
- The core claim is named honestly and precisely: "confidentiality here comes from having nothing to attack, not from attack-resistant infrastructure" — a real, quotable architectural thesis, not marketing filler.
- Tradeoffs are disclosed rather than hidden. "Egress is unrestricted, and that's a real residual risk this pattern does not close" directly undercuts the repo's own headline name rather than letting the branding oversell the security posture.
- Concrete, non-generic details throughout: the `desired_count`-as-dark-switch cost model, the two-policy IdP split with the specific Cloudflare `require`/`email_domain` gotcha, the repo-rename trust caveat on the OIDC role — the kind of specifics that only show up from actually building and debugging the thing.

Minor nitpicks, not disqualifying:
- "The dark switch" is a slightly precious bit of branding language amid otherwise plain, technical prose.
- The zero-ingress rationale is stated in near-identical language three separate times across README, architecture.md, and well-architected.md — defensible since each doc operates at a different altitude, but noticeable to a reader working through all three.

A reader clicking through from the blog post would come away thinking this person builds carefully and discloses tradeoffs honestly. No oversold claims, no hand-waving found.

### Skeptical Outsider

All three verification commands ran clean, and the README's factual claims check out. But the "reuse" story is thinner than it reads.

Findings, most significant first:

1. **"Reusable module" claim is validated once, not demonstrated twice.** README says a second app is "one more module block, not a second copy of the pattern." In the actual repo, `main.tf` has exactly one real instantiation (`module "example_app"`, nginx demo, `desired_count = 0`). `app.tf.example` is a `.example` file Terraform never loads (confirmed: only `main.tf` has an active `module` block). The claim of proven reuse rests on a template that has never been copied, filled in, and validated as a second real block.
2. "Terraform validate-clean" is true — ran it directly, succeeds cleanly.
3. "Standalone example, no ties to any shared Terraform library" is true — grepped the whole tree for backend/remote_state/hekton references, zero matches beyond the explanatory comment.
4. No hedge-free overclaiming found — the few "always/never" hits are narrow, accurate statements about specific mechanics, not sweeping security guarantees. Docs are otherwise unusually well-hedged.

Bottom line: the honesty/hedging is genuinely good and the two headline infra claims check out live. The one soft spot is the reuse story: asserted as proven but only exercised against one module call, with the second-app path resting on an untested template.
